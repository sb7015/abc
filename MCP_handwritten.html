1.What is MCP?

1.1Introduction

  • MCP stands for Model Context Protocol: an open standard for connecting AI applications to external tools, data sources and workflows.
  • Introduced by Anthropic in November 2024; since December 2025 it is governed by the Agentic AI Foundation under the Linux Foundation.
  • It works like a "USB-C port for AI": build a tool server once and any MCP-capable app (Claude, ChatGPT, VS Code, Cursor, your own agent) can use it.
  • Messages are JSON-RPC 2.0, carried over stdio (local) or Streamable HTTP (remote).

1.2Why MCP?

  • LLMs only know their training data and cannot reach live data, files, databases or APIs on their own.
  • Before MCP, every app × every tool needed its own integration: the M × N problem. MCP turns it into M + N: each app implements a client once, each tool implements a server once.
  • Tool servers become reusable, shareable and versioned, independent of which model or app uses them.

The model never talks to the server directly. The host lists the server's tools over MCP, gives them to the model, and when the model asks for a tool the host runs it over MCP and returns the result to the model.

1.4Key Points

  • Open, vendor-neutral protocol with official SDKs (Python, TypeScript, Java, Kotlin, C#, Go, Rust and others).
  • Standardizes discovery (what can this server do?) and execution (do it) of tools and data.
  • Works with any LLM; MCP is independent of the model provider.
  • Security is the implementer's job: MCP defines OAuth-based authorization for HTTP, but consent, sandboxing and least privilege are up to hosts and servers.

1.5Common Use Cases

  • Accessing real-time data (weather, prices, tickets, monitoring)
  • Reading and writing files; searching code bases
  • Querying databases and warehouses
  • Acting in SaaS apps (GitHub, Slack, Jira, Notion, Google Drive)
  • Giving AI agents a reusable, governed tool layer

2.4How a Tool Call Actually Works

  1. The host connects to the server and calls tools/list to get each tool's name, description and JSON Schema.
  2. The host passes those definitions to the LLM as function-calling tools, along with the user's message.
  3. The model decides a tool is needed and returns a tool call (name + arguments).
  4. The host (often after user approval) sends tools/call to the server.
  5. The server executes it and returns content (and optionally structuredContent), with isError on failure.
  6. The host feeds the result back to the model, which answers the user or calls more tools.

2.5Key Benefits

  • One server works with many hosts; one host works with many servers.
  • Dynamic discovery: hosts learn what servers can do at runtime.
  • Clear separation: the model decides, the host governs, the server executes.

3.MCP Architecture

3.1Overview

  • Client–server architecture with two layers: a data layer (JSON-RPC messages: primitives, notifications) and a transport layer (stdio or Streamable HTTP, plus auth).
  • A host can connect to many servers at once, each through its own client.
  • Servers can be local processes (full access to the machine they run on) or remote services (shared, behind OAuth).

3.4Key Characteristics

  • Standardized, model-agnostic protocol.
  • Composable: many servers per host, many hosts per server.
  • Stateless by default since 2026-07-28, which makes remote servers easy to scale behind a load balancer.
  • Extensible through capabilities and official extensions (e.g. MCP Apps, tasks).

4.Server Primitives: Tools, Resources, Prompts

4.1Tools

  • Executable functions the model can invoke: search, query a DB, create a ticket, send email.
  • Each tool has a name, description, inputSchema (JSON Schema), optional outputSchema, and optional annotations.
  • Annotations are hints for the host: readOnlyHint, destructiveHint, idempotentHint, openWorldHint. Hosts use them for approval UX, but must not trust them from untrusted servers.
  • Results contain content (text, images, audio, resource links) and optionally typed structuredContent matching outputSchema.

4.2Resources

  • Read-only data identified by a URI, e.g. file:///docs/readme.md, postgres://db/users/schema.
  • Application-controlled: the host or user decides what to attach as context; the model does not "call" resources.
  • Fixed resources come from resources/list; parameterized ones are resource templates such as notes://{topic}.
  • Clients can subscribe to changes (via subscriptions/listen in 2026-07-28).

4.3Prompts

  • Reusable, parameterized message templates the user chooses, often shown as slash commands.
  • Examples: "summarize this document", "review this PR", "draft an incident report".
  • prompts/get returns ready-to-send messages with arguments filled in.

4.4Notifications & Errors

  • Notifications are one-way messages: notifications/tools/list_changed, notifications/resources/updated, notifications/progress.
  • Protocol errors are JSON-RPC errors (unknown method -32601, invalid params -32602).
  • Tool execution errors are normal results with "isError": true, so the model can read the message and recover (e.g. fix its SQL and retry).

5.3Transports

TransportHow it worksUse case
stdioHost launches the server as a subprocess; newline-delimited JSON-RPC on stdin/stdout; logs go to stderrLocal tools, IDEs, desktop apps
Streamable HTTPOne endpoint (e.g. /mcp). Client POSTs each message; server replies with JSON or an SSE stream (for progress or multiple messages)Remote and shared servers, SaaS, enterprise
HTTP+SSE (old)Separate SSE and POST endpointsDeprecated since 2025-03-26. Do not use for new work.
RememberSSE still appears inside Streamable HTTP as a response format. What's deprecated is the old two-endpoint SSE transport.

5.4Lifecycle

Spec ≤ 2025-11-25: stateful handshake

  1. Client sends initialize with protocol version, capabilities, client info.
  2. Server replies with its version, capabilities, server info.
  3. Client sends notifications/initialized.
  4. Normal operation inside a session (Mcp-Session-Id header on HTTP).

Spec 2026-07-28: stateless

  1. No handshake and no sessions.
  2. Every request carries protocol version and client capabilities in _meta.
  3. Optional server/discover returns supported versions and capabilities up front.
  4. Server-to-client questions use Multi Round-Trip Requests (input_required + retry).

The official SDKs handle both: the v2 Python Client tries server/discover and falls back to initialize for older servers.

5.5Version Timeline

SpecKey changes

7.Use Cases & MCP vs Function Calling

7.1Real-World Examples

  • GitHub server: read code, open PRs, triage issues from Claude, ChatGPT or an IDE.
  • Notion / Google Drive / Confluence servers: search and update documents.
  • Database servers: natural-language analytics over Postgres, Snowflake, BigQuery.
  • Enterprise: one governed MCP gateway exposing internal APIs to every approved AI app.

7.2Industry Applications

  • Software: code search, CI logs, incident triage, deployments.
  • Analytics: query warehouses, generate reports.
  • Insurance / healthcare: policy or claims lookups through audited, read-only tools; sensitive data stays behind the server's access controls.
  • Finance: transaction and risk queries with strict scopes and audit trails.

7.3MCP vs Function Calling

They are not alternatives. Function calling is how a model asks for a tool. MCP is how an application discovers and runs tools that live in separate, reusable servers. In practice MCP tools are handed to the model through function calling.

Function callingMCP
What it isA model API feature: the model outputs a structured tool callA protocol between an AI app and tool servers
Where tools are definedIn each app's code, per provider formatOnce, in an MCP server, reusable by any host
DiscoveryStatic list sent with each requestDynamic tools/list, change notifications
ExecutionYour app's codeThe MCP server (local process or remote service)
Beyond toolsNoResources, prompts, elicitation, auth, progress

7.4Key Takeaways

  • ★ MCP is the integration layer; function calling is the model interface.
  • ★ Value grows with reuse: one server, many apps and agents.
  • ★ Security depends on the implementation, not on the protocol alone.

8.Build an MCP Server (Python)

8.1Setup

pip install "mcp[cli]"     # official SDK, v2.x, Python 3.10+

In SDK v2, FastMCP is renamed MCPServer. Type hints and the docstring become the tool's JSON Schema and description automatically.

8.2A Server with One Tool, One Resource, One Prompt

server.py

from mcp.server import MCPServer

mcp = MCPServer("Notes Demo")


@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b


@mcp.resource("notes://{topic}")
def get_note(topic: str) -> str:
    """Return the study note for a topic."""
    return f"Study notes about {topic}..."


@mcp.prompt()
def summarize(text: str) -> str:
    """Ask the model to summarize a piece of text."""
    return f"Summarize the following in 5 bullet points:\n\n{text}"


if __name__ == "__main__":
    mcp.run()  # stdio (local). For remote use: mcp.run(transport="streamable-http")

8.3Run and Inspect

mcp dev server.py                                    # opens the MCP Inspector to test it
mcp run server.py --transport streamable-http        # serve at http://localhost:8000/mcp

8.5Good Practices

  • Write tool descriptions for the model: say what the tool does, when to use it, and what each argument means.
  • Return typed results (pydantic models) so clients get structuredContent and an outputSchema.
  • Raise ToolError for expected failures so the model sees a useful message; other exceptions are hidden as generic errors.
  • Never print to stdout in a stdio server; it corrupts the protocol stream. Log to stderr.
  • Use async I/O (httpx.AsyncClient, async DB drivers) for network-bound tools.

from mcp import Client


async def main() -> None:
    async with Client("http://localhost:8000/mcp") as client:
        tools = await client.list_tools()

            print(tool.name, "-", tool.description)

9.4Without the SDK (raw HTTP, for understanding only)

A bare requests.post with only Content-Type is rejected by a real server (HTTP 400). A raw call needs the Accept header, the MCP headers and the _meta block:

raw_http.py

import asyncio

import httpx

URL = "http://localhost:8000/mcp"
PROTOCOL = "2026-07-28"


async def call_tool(name: str, arguments: dict) -> dict:
    payload = {
        "jsonrpc": "2.0",
        "id": 1,
        "method": "tools/call",
        "params": {
            "name": name,
            "arguments": arguments,
            "_meta": {
                "io.modelcontextprotocol/protocolVersion": PROTOCOL,
                "io.modelcontextprotocol/clientCapabilities": {},
                "io.modelcontextprotocol/clientInfo": {"name": "raw-demo", "version": "1.0"},
            },
        },
    }
    headers = {
        "Content-Type": "application/json",
        "Accept": "application/json, text/event-stream",
        "MCP-Protocol-Version": PROTOCOL,
        "Mcp-Method": "tools/call",
        "Mcp-Name": name,
    }
    async with httpx.AsyncClient() as http:
        response = await http.post(URL, json=payload, headers=headers)
        response.raise_for_status()
        return response.json()


print(asyncio.run(call_tool("add", {"a": 2, "b": 3})))
Use the SDK in practiceIt handles version negotiation, SSE responses, retries, auth and older servers for you.

10.Connect MCP to an LLM: the Host Loop

10.1What a Host Does

10.2Example: Claude + an MCP Server

pip install "mcp[cli]" anthropic

host_loop.py

import asyncio

from anthropic import AsyncAnthropic
from mcp import Client, StdioServerParameters

MODEL = "claude-sonnet-5-5"
server = StdioServerParameters(command="python", args=["db_server.py"])
llm = AsyncAnthropic()  # reads ANTHROPIC_API_KEY


def to_claude_tools(mcp_tools) -> list[dict]:
    """MCP tool definitions -> Claude API tool definitions."""
    tools = [
        {"name": t.name, "description": t.description or "", "input_schema": t.input_schema}
        for t in mcp_tools
    ]
    tools[-1]["cache_control"] = {"type": "ephemeral"}  # cache the static tool list
    return tools


async def ask(question: str) -> str:
    async with Client(server) as mcp:                       # host opens one client per server
        tools = to_claude_tools((await mcp.list_tools()).tools)
        messages = [{"role": "user", "content": question}]

        while True:
            reply = await llm.messages.create(
                model=MODEL, max_tokens=1024, tools=tools, messages=messages
            )
            if reply.stop_reason != "tool_use":             # model answered: done
                return "".join(b.text for b in reply.content if b.type == "text")

            messages.append({"role": "assistant", "content": reply.content})
            calls = [b for b in reply.content if b.type == "tool_use"]
            # the MODEL chose these tools; the host executes them over MCP, in parallel
            results = await asyncio.gather(*(mcp.call_tool(c.name, c.input) for c in calls))
            messages.append({"role": "user", "content": [
                {
                    "type": "tool_result",
                    "tool_use_id": call.id,
                    "content": [{"type": "text", "text": block.text}
                                for block in result.content if block.type == "text"],
                    "is_error": result.is_error,
                }
                for call, result in zip(calls, results)
            ]})


print(asyncio.run(ask("Which users live in Jaipur?")))
NotesThe MCP wire format uses inputSchema; the Claude API expects input_schema. That conversion is the host's job. Tool definitions are static, so they are marked for prompt caching. Real hosts also ask the user before running tools with side effects.

12.3Example: Read-Only SQLite Server

db_server.py

import sqlite3
from contextlib import closing

from pydantic import BaseModel

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

DB_PATH = "app.db"
mcp = MCPServer("SQLite Reader")
READ_ONLY = ToolAnnotations(readOnlyHint=True)


class QueryResult(BaseModel):  # typed return -> outputSchema + structuredContent
    columns: list[str]
    rows: list[list]


def connect() -> sqlite3.Connection:
    # mode=ro opens the database read-only, so no tool can change data
    return sqlite3.connect(f"file:{DB_PATH}?mode=ro", uri=True)


@mcp.tool(annotations=READ_ONLY)
def list_tables() -> list[str]:
    """List all tables in the database."""
    with closing(connect()) as conn:
        rows = conn.execute("SELECT name FROM sqlite_master WHERE type = 'table'").fetchall()
    return [row[0] for row in rows]


@mcp.tool(annotations=READ_ONLY)
def describe_table(table: str) -> list[dict]:
    """Return the column names and types of a table."""
    if table not in list_tables():  # allow-list check blocks SQL injection via the name
        raise ToolError(f"Unknown table: {table}")
    with closing(connect()) as conn:
        columns = conn.execute(f"PRAGMA table_info({table})").fetchall()
    return [{"name": col[1], "type": col[2]} for col in columns]


@mcp.tool(annotations=READ_ONLY)
def read_query(sql: str, limit: int = 50) -> QueryResult:
    """Run one read-only SELECT query and return its columns and rows."""
    if not sql.lstrip().lower().startswith("select"):
        raise ToolError("Only SELECT queries are allowed")
    with closing(connect()) as conn:
        cursor = conn.execute(sql)
        rows = cursor.fetchmany(limit)
        columns = [d[0] for d in cursor.description]
    return QueryResult(columns=columns, rows=[list(r) for r in rows])


if __name__ == "__main__":
    mcp.run()

A blocked query returns an execution error the model can read:

{"content": [{"type": "text", "text": "Error executing tool read_query: Only SELECT queries are allowed"}], "isError": true}

12.5Key Points

  • Connect with a read-only database user or read-only mode; give write tools separate names and approvals.
  • Allow-list identifiers (tables, columns) and use parameters for values to stop SQL injection.
  • Cap rows (limit) and add query timeouts to protect the database and the context window.
  • Mark tools with readOnlyHint / destructiveHint so hosts can tune approval prompts.

13.3Example: Sandboxed Workspace Server

fs_server.py

from pathlib import Path

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

ROOT = Path("./workspace").resolve()  # the only folder this server may touch
mcp = MCPServer("Workspace Files")


def safe_path(relative: str) -> Path:
    """Resolve a path and refuse anything outside ROOT (blocks ../ traversal)."""
    path = (ROOT / relative).resolve()
    if not path.is_relative_to(ROOT):
        raise ToolError(f"Path is outside the workspace: {relative}")
    return path


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def list_directory(path: str = ".") -> list[str]:
    """List files and folders inside a workspace directory."""
    folder = safe_path(path)
    return sorted(p.name + ("/" if p.is_dir() else "") for p in folder.iterdir())


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def read_file(path: str) -> str:
    """Read a UTF-8 text file from the workspace."""
    file = safe_path(path)
    if not file.is_file():
        raise ToolError(f"File not found: {path}")
    return file.read_text(encoding="utf-8")


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def search_files(pattern: str) -> list[str]:
    """Find workspace files matching a glob pattern, e.g. '**/*.log'."""
    return sorted(str(p.relative_to(ROOT)) for p in ROOT.glob(pattern) if p.is_file())


@mcp.tool(annotations=ToolAnnotations(destructiveHint=True))
def write_file(path: str, content: str) -> str:
    """Create or overwrite a text file in the workspace."""
    file = safe_path(path)
    file.parent.mkdir(parents=True, exist_ok=True)
    file.write_text(content, encoding="utf-8")
    return f"Wrote {len(content)} characters to {path}"


@mcp.resource("workspace://{name}")
def workspace_file(name: str) -> str:
    """Expose top-level workspace files as resources the app can attach as context."""
    return read_file(name)


if __name__ == "__main__":
    mcp.run()

14.3Example: Async Weather Server (no API key needed)

weather_server.py

import httpx
from pydantic import BaseModel

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

mcp = MCPServer("Weather")
GEO_URL = "https://geocoding-api.open-meteo.com/v1/search"
FORECAST_URL = "https://api.open-meteo.com/v1/forecast"


class Weather(BaseModel):
    city: str
    temperature_c: float
    humidity_pct: float


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True, openWorldHint=True))
async def get_weather(city: str) -> Weather:
    """Get the current temperature and humidity for a city."""
    async with httpx.AsyncClient(timeout=10) as http:
        geo = await http.get(GEO_URL, params={"name": city, "count": 1})
        geo.raise_for_status()
        places = geo.json().get("results")
        if not places:
            raise ToolError(f"City not found: {city}")
        place = places[0]

        forecast = await http.get(FORECAST_URL, params={
            "latitude": place["latitude"],
            "longitude": place["longitude"],
            "current": "temperature_2m,relative_humidity_2m",
        })
        forecast.raise_for_status()
        current = forecast.json()["current"]

    return Weather(
        city=place["name"],
        temperature_c=current["temperature_2m"],
        humidity_pct=current["relative_humidity_2m"],
    )


if __name__ == "__main__":
    mcp.run(transport="streamable-http")  # serves http://localhost:8000/mcp

14.4Key Points

  • Use async HTTP clients so one slow API doesn't block other tool calls.
  • Set timeouts, handle rate limits, and return clear ToolError messages.
  • Mark tools that reach the outside world with openWorldHint.
  • Return compact, structured data; don't dump raw API payloads into the model's context.

16.Security, Authentication & Deployment

16.1Authorization Model (HTTP transport)

  • Based on OAuth 2.1. The MCP server is an OAuth resource server; a separate (or co-hosted) authorization server issues tokens.
  • The server publishes Protected Resource Metadata (RFC 9728) and answers unauthenticated requests with 401 + WWW-Authenticate: Bearer resource_metadata="...".
  • Clients use PKCE and the resource parameter (RFC 8707) so tokens are bound to that specific server (audience).
  • Client registration: Client ID Metadata Documents (preferred), pre-registration, or Dynamic Client Registration (deprecated).
  • Servers must reject tokens not issued for them and must not pass client tokens through to downstream APIs.
  • stdio servers don't use this flow; they read credentials from the environment.

16.2Example: Protecting a Server

auth_server.py

from mcp.server import MCPServer
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings

SERVER_URL = "http://localhost:8000/mcp"


class MyTokenVerifier:
    """Validate bearer tokens issued by your authorization server.

    Production: verify the JWT signature against the issuer's JWKS (or call its
    introspection endpoint) and confirm the token's audience is SERVER_URL.
    """

    async def verify_token(self, token: str) -> AccessToken | None:
        if token != "demo-token":  # placeholder check, demo only
            return None
        return AccessToken(token=token, client_id="demo-client",
                           scopes=["notes:read"], resource=SERVER_URL)


mcp = MCPServer(
    "Protected Notes",
    token_verifier=MyTokenVerifier(),
    auth=AuthSettings(
        issuer_url="https://auth.example.com",  # your OAuth 2.1 authorization server
        resource_server_url=SERVER_URL,         # this MCP server is the protected resource
        required_scopes=["notes:read"],
        validate_token_resource=True,           # reject tokens issued for other servers
    ),
)


@mcp.tool()
def get_note(topic: str) -> str:
    """Return a private note."""
    return f"Private notes about {topic}"


if __name__ == "__main__":
    mcp.run(transport="streamable-http")

16.4MCP-Specific Threats

ThreatWhat happensMitigation
Prompt injection via tool outputA web page, email or file contains instructions the model followsTreat tool output as data; require approval for side effects; limit what tools can do
Tool poisoningA malicious server hides instructions in tool descriptionsInstall only trusted servers; review descriptions; pin versions
Rug pullTool definitions change after the user approved themWatch list_changed; re-approve on change; pin versions

16.5Best Practices

  • Least privilege: separate read and write tools, minimal scopes, read-only DB users.
  • Human approval for destructive or external actions.
  • Validate every input in the server (schemas, allow-lists, path checks).
  • Audit-log tool calls with user, arguments and results.
  • Rate-limit, set timeouts, and cap result sizes.
  • Keep secrets in a secret manager; rotate them.

17.3Interview Questions with Model Answers

  1. What is MCP and why does it matter? An open protocol that standardizes how AI apps discover and use external tools and data. It turns M×N custom integrations into M+N reusable ones.
  2. Host vs client vs server? The host is the AI app (runs the LLM, handles consent); it creates one client per server; the server exposes tools, resources and prompts.
  3. Tools vs resources vs prompts? Tools are model-controlled actions; resources are application-controlled read-only data by URI; prompts are user-chosen templates.
  4. Does the LLM speak MCP? No. The host fetches tool definitions over MCP, passes them to the model via function calling, and executes the model's tool calls over MCP.
  5. Function calling vs MCP? Function calling is the model's interface for requesting a tool; MCP is the protocol for discovering and running tools in reusable servers. They are complementary.
  6. Which transports exist and when do you use each? stdio for local subprocess servers; Streamable HTTP for remote or shared servers. HTTP+SSE is deprecated.
  7. What changed in the 2026-07-28 spec? MCP became stateless: no initialize handshake or sessions, version and capabilities in each request's _meta, server/discover, multi-round-trip requests; sampling and roots deprecated.
  8. How does authentication work? OAuth 2.1 on HTTP: the server is a resource server publishing RFC 9728 metadata; clients use PKCE and resource indicators; tokens are audience-bound; no token passthrough.
  9. Protocol error vs tool error? Protocol errors are JSON-RPC errors (bad method or params). Tool failures return a normal result with isError: true so the model can recover.
  10. How do you connect MCP to a database safely? Read-only credentials, allow-listed identifiers, parameterized values, row limits, timeouts, and separate approved write tools.
  11. How do you build a custom server? With MCPServer: decorate typed Python functions with @mcp.tool(); type hints become the schema; run over stdio or Streamable HTTP.
  12. Top MCP security risks? Prompt injection through tool output, tool poisoning, rug pulls, confused deputy, over-broad scopes, and untrusted local servers.
  13. How do you build a multi-agent system with MCP? Each agent is a host with its own MCP clients; share servers as the tool layer; use an orchestrator (LangGraph) or A2A for agent-to-agent communication.
  14. How do you handle hundreds of tools? Load only relevant servers per task, group tools, search tools on demand, and cache static tool lists to save tokens.

17.4Tips for Interview Preparation

  • Build one server and one client end to end; test with mcp dev (Inspector).
  • Be able to sketch the host–client–server diagram and the tool-call loop.
  • Know the transports, the lifecycle and the 2026 stateless change.
  • Explain security trade-offs concretely (consent, scopes, sandboxing).
  • Know how MCP fits with function calling, LangGraph and A2A.

17.5Key Takeaways

  • MCP is the standard integration layer between AI applications and the outside world.
  • The model decides, the host governs, the server executes.
  • Build servers once and reuse them across every MCP-capable app and agent.
  • Security and good tool design are what make MCP production-ready.
